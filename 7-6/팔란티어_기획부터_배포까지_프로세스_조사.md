# 팔란티어(Palantir) 기획→배포 프로세스 조사

조사일: 2026-07-06

## 핵심 특징: 전통적 순서의 역전

일반 IT 서비스 기업은 **기획 → 개발 → 배포** 순서를 따르지만, 팔란티어는 이를 뒤집는다.

> **배포 → 개발(검증) → 제품화(계획)**

고객 현장에서 급한 문제가 생기면 완벽한 기획서를 만들기 전에 실제 데이터로 프로토타입부터 배포하고, 효과가 입증된 것만 정식 기능으로 편입시킨다. "현장에서 먼저 작동하게 만들고 나중에 다듬는" 실용주의 모델이다.

## 단계별 프로세스

**1) 문제 정의**

세 가지 질문으로 구조화한다.
- 어떤 의사결정이 필요한가 (What decision?)
- 해결 시 임팩트는 얼마인가 (How much impact?)
- 데이터는 준비되어 있는가 (Where is the data?)

**2) Bootcamp (0→1, 1~5일)**

기능 목록으로 시작하지 않고, 고객의 실제 데이터를 갖고 1~2개 고가치 문제에 집중한 급속 프로토타이핑 스프린트를 진행한다. 데모나 목업이 아닌, 실제 데이터로 작동하는 애플리케이션을 며칠 안에 만들어 보여준다. (전통적 파일럿은 통상 1~3개월 소요되는 것과 대비)

**3) 초기 배포·운영 (Palantir가 직접 운영)**

검증 초기 단계에서는 팔란티어가 키를 넘기고 떠나지 않고, 직접 워크플로우를 구축·배포·운영한다. 이때 배포/업데이트/컴플라이언스는 Apollo 플랫폼이 담당한다.

**4) 스케일업 (8~12주)**

단일 유스케이스 프로토타입을 복잡한 사이트 전체의 완전한 프로덕션 환경으로 확장하는 단계.

**5) 고객 자립화 — Center of Excellence(CoE)**

시간이 지나며 팔란티어는 고객사 내부에 플랫폼 오너, 권한 관리자 등 역할을 갖춘 CoE를 세워, 고객이 스스로 플랫폼을 운영할 수 있도록 이관한다.

**6) 계약·매출 구조의 확장**

계약은 작은 규모(짧은 부트캠프 + 제한된 라이선스)로 시작해, 가치가 입증되면 추가 유스케이스·워크플로우·데이터 도메인이 붙는다. 시간이 지날수록 매출 구성은 서비스 중심에서 구독형 소프트웨어 매출 중심으로 이동한다.

## 현장 중심 조직 구조

- **FDSE / "Delta" (전진배치 소프트웨어 엔지니어)**: 고객사에 상주하며 실제 프로덕션급 코드를 작성하고, 데이터 파이프라인 설계·온톨로지 모델링을 담당. 팔란티어 코어 제품 아키텍트와 동일한 기술 면접을 통과한 인력.
- **Deployment Strategist / "Echo"**: 대개 비(非)엔지니어 도메인 전문가(전직 군인, 임상의, 회계 포렌식 전문가 등)로, 고객 관계와 내부 정치·도입(adoption)을 담당.
- 두 역할 모두 본사 승인 없이 고객 문제 해결에 필요한 신규 기술을 현장에서 직접 개발할 권한을 가짐 — "현장에 대한 급진적 존중"이 핵심 원칙.
- 엔지니어의 성과 기준은 "프로젝트 완료일"이 아니라 "문제가 실제로 해결되었는가".

## 기술 플랫폼 구조

| 계층 | 역할 |
|---|---|
| **Foundry** | 데이터 통합 + 온톨로지(조직의 데이터를 레고 블록처럼 모듈화해 비개발자도 조립 가능하게 함) |
| **AIP** | AI 계층 — CI/CD 개념을 물리적 세계(운영)까지 확장한 "딜리버리를 위한 운영체제" |
| **Apollo** | 지속적 배포/딜리버리 플랫폼. Hub(중앙 오케스트레이션)–Spoke(개별 격리/폐쇄망 환경) 구조로 온톨로지·파이프라인·워크플로우·코드저장소·UI를 격리된 보안 환경에도 배포. 주당 수만 건의 릴리스를 오케스트레이션 |

## 요약

팔란티어는 "완벽한 기획서" 대신 부트캠프(실데이터 프로토타입) → 현장 상주 배포·운영 → 스케일업 → 고객 자립(CoE) → 구독 매출 전환이라는, 배포를 가장 먼저 두는 역순 프로세스로 움직이며, 이는 FDE/Deployment Strategist라는 현장 밀착형 조직과 Foundry-AIP-Apollo라는 기술 스택이 뒷받침한다.

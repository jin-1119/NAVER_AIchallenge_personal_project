## 1. 기획 (Planning)

### 1) 아이디어 발굴 및 시장 조사

IT 서비스 기획의 출발점은 "고객이 어떤 문제를 불편해하는가"를 찾는 문제 발견(Problem Discovery) 과정이다. 아이디어는 사내 제안, 고객 VOC(Voice of Customer), 데이터 기반 이상 징후 발견, 경영진 지시 등 다양한 경로로 소싱되며, 이후 시장 조사 단계로 이어진다. 시장 조사는 일반적으로 세 갈래로 진행된다.

- **시장 동향 파악**: 시장 규모, CAGR 등 정량 지표와 기술·사회문화적 트렌드를 분석 (거시환경분석 PEST 프레임워크 활용)
- **경쟁사 분석**: 경쟁사의 강약점, 시장 점유율, 제품/가격/마케팅 전략을 SWOT(강점·약점·기회·위협), 3C(Customer·Competitor·Company) 프레임워크로 분석
- **소비자(사용자) 조사**: 설문, 인터뷰, FGI 등을 통해 구매 동기·이용 채널·불편 지점(Pain Point)을 파악

이후 STP 전략(Segmentation-세분화 → Targeting-타겟 선정 → Positioning-차별화 포지셔닝)으로 이어져, "누구에게 어떤 가치를 제공할 것인가"를 구체화한다. 실무에서는 보통 PEST → 3C → SWOT 순서로 분석 범위를 좁혀가며 설득력 있는 근거를 쌓는 방식을 취한다.

해외 사례로는 **아마존의 Working Backwards(워킹 백워드)** 방법론이 널리 인용된다. 아이디어에서 출발해 제품을 만드는 대신, 고객에서 출발해 "이 제품이 출시되면 어떤 보도자료(PR)가 나갈 것인가"를 먼저 작성하고 예상 Q&A(FAQ)를 채워가며 기획을 구체화하는 방식으로, 국내 대기업 프로젝트에도 도입된 사례가 있다.

### 2) 요구사항 정의: PRD, 사용자 스토리, 우선순위 결정

시장 조사와 아이디어 검증이 끝나면 **PRD(Product Requirements Document, 제품 요구사항 정의서)** 작성으로 넘어간다. PRD에는 사용자 문제 정의, 목표(Goal)와 성공 지표, 사용자 조사 결과, 해결 방안 옵션과 트레이드오프, 기술적 제약, UX 고려사항, 일정과 리소스가 포함되며 개발자·디자이너·영업·CX 등 이해관계자와 공유되어 합의를 거친다. 규모가 큰 조직에서는 1-Pager(요약형)와 6-Pager(상세형) 문서를 병행하기도 한다.

세부 기능 명세는 **사용자 스토리(User Story)** 형식으로 작성된다. "[사용자 유형]으로서, 나는 [목표]를 원한다, 왜냐하면 [이유] 때문이다"라는 템플릿이 표준이며, Epic(큰 단위 기능) 아래 여러 User Story를 두는 계층 구조로 애자일/스크럼 백로그에 반영된다.

우선순위 결정에는 대표적으로 두 프레임워크가 쓰인다.

| 프레임워크 | 방식 | 적합한 상황 |
|---|---|---|
| **RICE** (Intercom 고안) | Reach(도달 범위)×Impact(영향력)×Confidence(확신도)÷Effort(투입 노력)로 점수화 | 사용자 수·전환율 등 정량 데이터 확보 시 |
| **MoSCoW** | Must have / Should have / Could have / Won't have 4단계 분류 | 리소스가 제한적이고 빠른 합의가 필요한 스타트업·초기 프로젝트 |

이 외 Kano 모델(만족도-충족도 매트릭스)도 기능 우선순위 판단에 함께 언급된다.

### 3) 참여 직군과 협업 방식

기획 단계에는 기획자/PM/PO, UX 디자이너, 개발 리드, 데이터 분석가, QA가 함께 참여한다. PM(Product Manager), PO(Product Owner), 서비스기획자라는 타이틀은 조직마다 경계가 다르게 쓰이지만 공통적으로 "문제 정의 → 해결안 도출 → 실행 조율"을 담당한다. **우아한형제들(배달의민족)** 사례에서는 기획·개발·디자인·QA가 하나의 목적 조직(스쿼드)으로 묶여 데일리 스탠드업을 진행하고, Figma(디자인 협업), Wiki·Jira(정책 문서·태스크 관리)를 사용하며 2주 단위 스프린트로 운영 개선 과제를 진행한다. 월별 회고와 분기별 워크숍을 통해 서비스 방향성을 조정한다.

데이터 분석가는 기획 단계에서 가설 검증, 데이터 기반 모니터링, 문제점 도출을 지원하는 역할을 하며, 최종적으로 문제를 정의하고 솔루션을 실행에 옮기는 책임은 기획자/PM에게 있다.

### 4) 대표적 기획 산출물/프레임워크

- **PRD**: 요구사항 정의서 (앞서 설명)
- **유저 시나리오/유저 플로우**: 사용자가 목표 달성을 위해 거치는 행동 흐름을 시각화
- **와이어프레임(초안)**: 화면 단위 정보구조·레이아웃 스케치, 이후 디자이너의 UI 시안으로 발전
- **OKR (Objective & Key Results)**: 기획 방향을 정량 목표(Key Results)와 정성 목표(Objective)로 정리
- **더블 다이아몬드(Double Diamond)**: 발견(Discover)→정의(Define)→개발(Develop)→전달(Deliver)의 발산-수렴 반복 구조. 디자인씽킹(공감-정의-아이디어 발상-프로토타입-테스트)과 함께 UX/서비스 기획 초기 단계에서 자주 활용
- **PR/FAQ**: 아마존 워킹 백워드의 핵심 산출물

### 5) 실제 기업 사례 요약

| 기업 | 특징 |
|---|---|
| 우아한형제들(배민) | 기획·개발·디자인·QA 목적조직, Figma/Jira/Wiki 활용, 2주 스프린트, 분기 워크숍으로 방향성 재조정 |
| 아마존 | Working Backwards — PR/FAQ 작성이 기획의 출발점 |
| 국내 스타트업 전반 | MoSCoW, RICE 등 우선순위 프레임워크를 백로그 관리에 실무 도입 |

전반적으로 국내 IT 서비스 기업들의 기획 프로세스는 **"문제 발견(시장·경쟁사·사용자 조사) → 요구사항 정의(PRD·유저스토리) → 우선순위화(RICE/MoSCoW) → 다직군 협업 → OKR 기반 목표 정렬"**이라는 공통 골격을 가진다.

## 2. 디자인 (Design)

**프로세스 흐름**: 대부분의 IT 서비스 기업은 "사용자 리서치 → 정보구조(IA) 설계 → 와이어프레임 → 프로토타이핑 → 디자인 시스템 적용 → 디자인 QA"의 선형·반복 구조를 따른다.

- **사용자 리서치**: 정성 인터뷰, 사용성 테스트, 정량 로그 분석을 병행한다. 토스는 리서처 없이도 팀 스스로 리서치를 수행할 수 있도록 "리서치 자율주행 프로젝트"를 운영하며, 자체 특허 툴인 TNS(Toss Navigation Score)로 사용자가 원하는 기능을 얼마나 잘 찾는지와 같은 정성적 경험을 정량 지표로 측정한다.
- **정보구조(IA) 설계 및 와이어프레임**: 서비스 목표에 맞춰 메뉴/화면 트리를 구조화한 뒤 저해상도 와이어프레임으로 흐름을 검증한다. 구글벤처스가 고안한 **디자인 스프린트(Design Sprint)**가 대표적 방법론으로, 월(문제 정의)~금(사용자 테스트) 5일 동안 이해-발산-결정-프로토타입-테스트 과정을 거쳐 아이디어를 빠르게 검증한다.
- **프로토타이핑**: Figma가 사실상 업계 표준 툴로 자리잡았다. 인터랙션·트랜지션까지 시각적으로 전달하는 Prototype 기능을 활용해 기획-디자인-개발-QA가 하나의 파일에서 협업한다.
- **디자인 시스템 구축**: 토스의 **TDS(Toss Design System)**가 대표 사례로, 디자이너·개발자·기획자가 직군 구분 없이 같은 기준으로 협업하도록 수백 개의 컴포넌트·템플릿을 제공하며, 디자인 툴에 머물지 않고 실제 개발 코드와 연결되어 "제품을 구성하는 언어"로 기능한다.
- **디자인 QA**: 개발 완료 화면과 디자인 시안을 비교하는 단계로, Figma의 Design Lint, Contrast Checker, Pixel Perfect 같은 플러그인을 통해 디자인-구현 간 차이를 자동 점검하는 흐름이 확산되고 있다.

**요약 표**

| 단계 | 핵심 활동 | 대표 툴/방법론 |
|---|---|---|
| 사용자 리서치 | 인터뷰, 사용성 테스트, 정량 지표화 | 토스 TNS, 자체 리서치 프로그램 |
| IA/와이어프레임 | 화면 구조 설계, 초기 흐름 검증 | 디자인 스프린트(구글벤처스) |
| 프로토타이핑 | 인터랙션 시뮬레이션, 협업 리뷰 | Figma |
| 디자인 시스템 | 컴포넌트·토큰 표준화, 개발 연동 | 토스 TDS |
| 디자인 QA | 시안-구현 비교, 자동 검수 | Figma 플러그인, 코멘트 기반 QA |

## 3. 개발 (Development)

**방법론**: 국내외 IT 서비스 기업은 대부분 워터폴 대신 **애자일(Agile)**, 그중에서도 **스크럼(Scrum)**을 기본 골격으로 채택한다. 스크럼 팀은 스크럼 마스터·프로덕트 오너(PO)·개발팀으로 구성되며, 보통 1~2주 단위 스프린트로 반복 개발한다. 제품 백로그의 우선순위 관리 책임은 PO가 가지며, 스프린트 백로그는 해당 스프린트 목표 달성에 필요한 작업 목록으로 별도 관리된다. 쿠팡은 물류·고객경험개선팀 등에서 데이터 기반 반복 개선 루프에 스크럼을 접목하고 있고, 우아한형제들은 개발팀뿐 아니라 디자인·마케팅 조직까지 스크럼 운영을 확장한 사례를 공유했다.

**조직 구조**: 프론트엔드/백엔드/인프라(DevOps)가 기능별 길드 또는 하나의 프로덕트 스쿼드 안에 함께 배치되는 형태가 일반적이며, 서비스 단위로 쪼갠 "미션-스쿼드-챕터" 구조(스포티파이 모델 계열)를 변형해 쓰는 곳도 많다.

**기술 설계**:
- **ADR(Architecture Decision Record)**: 2011년 Michael Nygard가 제안한 개념으로, 애자일 프로젝트에서 아키텍처를 하나의 큰 문서가 아닌 "작고 지속적인 결정들의 집합"으로 기록하는 방식이다. 결정 배경(Context)·선택(Decision)·결과(Consequence)를 마크다운 등 경량 포맷으로 작성해 코드 저장소와 함께 버전 관리한다.
- **API/DB 설계 및 기술 스택 선정**: 서비스 요구사항, 트래픽 규모, 팀 숙련도, 유지보수 비용을 기준으로 스택을 결정하며 대형사는 대체로 표준 아키텍처 리뷰나 기술위원회 프로세스를 거친다.

**코드 관리 프로세스**:
- **브랜치 전략**: 전통적 **Git Flow**(master/develop + feature/release/hotfix 브랜치)에서 최근에는 **트렁크 기반 개발(Trunk-Based Development, TBD)**로 전환하는 흐름이 뚜렷하다. 국내 사례로 맘시터(맘편한세상) 백엔드팀은 main 브랜치 하나만 운용하며 짧은 수명의 feature 브랜치→PR→코드리뷰→CI 자동 테스트/품질 분석의 흐름을 따르고, 삼쩜삼(자비스앤빌런즈)은 모노레포 환경에 맞춰 TBD에 가까운 "SimGit Flow"를 자체 도입했다.
- **코드 리뷰 문화**: 우아한형제들은 코드리뷰 도입 배경(기술부채·컨벤션 불일치 해소)과 이후 리뷰 효율화 개선 과정을 지속적으로 공유하며, 페어 프로그래밍을 코드리뷰와 병행하는 팀도 소개하고 있다.
- **페어/몹 프로그래밍**: TBD 환경에서는 main에 직접 반영되는 만큼 안정성 확보 수단으로 페어 프로그래밍이 코드리뷰와 함께 권장되는 경향이 있다.

**요약 표**

| 영역 | 접근 방식 | 대표 사례 |
|---|---|---|
| 개발 방법론 | 스크럼(1~2주 스프린트, PO/SM/개발팀) | 쿠팡, 우아한형제들 |
| 아키텍처 문서화 | ADR(경량 마크다운, 버전관리) | Nygard 방법론 기반 확산 |
| 브랜치 전략 | Git Flow → Trunk-Based Development | 맘시터, 삼쩜삼(SimGit Flow) |
| 코드 리뷰 | PR 기반 리뷰 + CI 자동 검증 | 우아한형제들 |

## 4. 테스트/QA (Testing & QA)

### 4.1 테스트 피라미드와 테스트 단계

IT 서비스 기업들은 비용 효율성을 기준으로 테스트를 계층화하는 **테스트 피라미드(Test Pyramid)** 개념을 따른다. 하위 단계일수록 실행 속도가 빠르고 비용이 저렴하므로 많이 작성하고, 상위로 갈수록 적게 작성하는 구조다.

| 단계 | 대상 | 특징 | 실행 주체 |
|---|---|---|---|
| 단위 테스트 (Unit Test) | 함수/모듈 단위 | 가장 많이 작성, 결함 발견 비용이 가장 저렴 | 개발자 |
| 통합 테스트 (Integration Test) | 여러 컴포넌트 간 상호작용 | 단위-E2E 중간, 실행시간이 김 | 개발자/QA |
| E2E 테스트 (End-to-End Test) | 실제 사용자 시나리오 전체 흐름 | 가장 느리고 깨지기 쉬움, 최소한으로 작성 | QA/자동화팀 |

반대로 E2E·UI 테스트에만 의존하고 단위 테스트가 부실한 구조는 "아이스크림콘 안티패턴"으로 불리며, 테스트가 느리고 잘 깨지며 유지보수 비용이 급증하는 문제가 있다. 우아한형제들(배달의민족)은 프론트엔드 통합 테스트를 도입해 더 안전한 서비스 개발 체계를 구축했고, SK텔레콤 '에이닷' 웹서비스팀과 카카오모빌리티는 각각 E2E 테스트 도입기를 기술블로그에 공개했다(카카오모빌리티는 Cypress 기반 E2E 자동화 도입).

### 4.2 QA팀의 테스트 케이스 작성 및 회귀 테스트

QA팀은 신규/변경 기능에 대한 테스트 케이스(TC)를 문서화하고, 매 배포마다 기존 기능이 깨지지 않았는지 확인하는 **회귀 테스트(Regression Test)**를 수행한다. 실제로 한 QA 조직 사례에서는 6개 실행 환경 전체를 수행하던 수동 회귀 테스트가 약 6~7시간 걸리던 것을, UI 기반 E2E 자동화 도입 후 2~3시간으로 단축했다고 보고했다. 자동화로 확보한 시간은 QA 엔지니어가 탐색적 테스트(Exploratory Testing)나 테스트 케이스 고도화에 재투자하는 방식으로 활용된다.

### 4.3 자동화 테스트 도구 및 파이프라인 연계

프론트엔드는 Jest/Vitest(단위), Cypress·Playwright(E2E), 백엔드는 JUnit/pytest 등이 널리 쓰이며, 이 테스트들은 CI 파이프라인에 통합되어 PR/커밋마다 자동 실행된다.

### 4.4 베타 테스트 / 내부 테스트(Dogfooding)

정식 출시 전 실제 사용자 환경에서 검증하는 단계로 크게 두 가지가 있다.
- **도그푸딩(Dogfooding)**: 자사 임직원이 자사 제품/서비스를 실무에서 직접 사용하며 결함과 불편함을 조기 발견하는 관행. 구글은 검색, Gmail, Drive 등 자사 서비스를 전사적으로 상시 사용하며 발견된 이슈를 제품 개선에 반영하는 것으로 알려져 있다.
- **베타 테스트/내부 테스트**: Google Play Console은 '내부 테스트-비공개 테스트-공개 테스트' 3단계 트랙을 제공해, 소수의 내부 인원부터 시작해 점차 넓은 사용자군으로 테스트를 확대하는 구조를 지원한다. 이는 점진적 배포(카나리·피처 플래그) 개념과 맞닿아 있다.

## 5. 배포 (Deployment)

### 5.1 CI/CD 파이프라인

**지속적 통합(CI)**은 코드 변경분을 자주 통합·빌드·자동 테스트하는 것, **지속적 배포/제공(CD)**은 검증된 빌드를 자동으로 운영 환경까지 내보내는 것을 의미한다. 일반적인 파이프라인은 "코드 커밋 → 자동 빌드 → 테스트 실행 → 스테이징 배포 → 운영 배포" 순으로 진행된다.

| 구분 | 도구 | 역할 |
|---|---|---|
| CI (빌드/테스트) | Jenkins, GitHub Actions, GitLab CI | 코드 변경 시 빌드·테스트 실행, 아티팩트(컨테이너 이미지 등) 생성 |
| CD (배포) | ArgoCD, FluxCD | Git에 선언된 상태를 감시해 실제 클러스터 상태를 일치시키는 GitOps 방식 |

가장 흔한 구성은 "GitHub Actions/GitLab CI(빌드·테스트) → 컨테이너 이미지·매니페스트를 Git에 반영 → ArgoCD가 변경을 감지해 쿠버네티스 클러스터에 자동 반영"하는 **GitOps** 아키텍처다.

### 5.2 배포 전략

- **롤링 업데이트(Rolling Update)**: 인스턴스를 순차적으로 교체하는 가장 기본적인 무중단 배포 방식.
- **블루-그린 배포(Blue-Green)**: 운영(Blue)과 대기(Green) 두 환경을 동일하게 구성해두고, 신버전 배포 후 트래픽을 한 번에 전환. 즉시 롤백이 가능하다. Netflix는 이를 "Red/Black 배포"라 부른다.
- **카나리 배포(Canary)**: 일부 서버/사용자에게만 신버전을 노출해 지표를 관찰한 뒤 문제가 없으면 점진적으로 확대. Netflix는 자체 오픈소스 도구 **Kayenta**로 신구 버전의 핵심 지표를 자동 비교해 이상 감지 시 자동으로 카나리를 중단한다. 또한 Chaos Monkey 등 Chaos Engineering 도구로 상시 장애 내성을 검증한다.
- **피처 플래그(Feature Flag/Toggle)**: 배포(코드 반영)와 릴리즈(사용자 노출)를 분리하는 기법. 우아한형제들은 기능 노출 비율 조정으로, 당근마켓(당근페이)은 권한 토글→카나리 토글의 단계적 방식으로 점진적 배포를 수행한다.

### 5.3 배포 승인 프로세스와 거버넌스

- **코드 리뷰/PR 승인**: 최소 1~2인의 동료 리뷰·승인이 있어야 머지 가능.
- **릴리즈 매니저 최종 승인**: 코드 리뷰·QA를 통과해도 타이밍(장애 위험 시점 회피 등)을 이유로 배포를 보류할 권한.
- **코드 프리즈(Code Freeze)**: 특정 시점(대형 이벤트, 연휴 등) 이후 신규 변경 반영을 중단.
- **배포 체크리스트**: 테스트 결과·릴리스 공지·코드 검토 완료 여부·배포 검증(헬스체크·모니터링 지표)을 항목별로 확인.
- **릴리스 노트 작성**: 변경 사항·영향 범위·롤백 방법 등을 문서화.

### 5.4 롤백 전략

블루-그린 방식은 트래픽 스위치만으로 즉시 롤백, 카나리 방식은 자동화된 지표 비교로 이상 감지 시 자동 롤백, 피처 플래그 방식은 코드 재배포 없이 플래그만 끄면 즉시 원복 — 가장 빠른 롤백 수단으로 평가된다.

## 6. 운영 및 모니터링 (Operations & Monitoring)

배포 이후 서비스는 "만들고 끝"이 아니라 **관측(Observability) → 대응(Response) → 측정(Measurement) → 개선(Improvement)**의 사이클로 들어간다.

### 6.1 모니터링 및 로깅

현대적인 운영 체계는 **Observability(관측 가능성)의 3요소** — 메트릭(Metrics), 로그(Logs), 트레이스(Traces) — 를 통합적으로 수집한다.

| 영역 | 대표 도구 | 역할 |
|---|---|---|
| APM/인프라 모니터링 | Datadog, New Relic, Dynatrace, Grafana+Prometheus | 응답시간, 에러율, 리소스 사용량 등 시계열 메트릭 수집·시각화 |
| 로그 수집/분석 | ELK(Elasticsearch-Logstash-Kibana), Splunk, Loki | 서버·애플리케이션 로그 중앙 집중화 및 검색 |
| 분산 트레이싱 | Jaeger, Zipkin, OpenTelemetry | 마이크로서비스 간 요청 흐름 추적 |
| 알림(Alerting) | PagerDuty, Grafana OnCall, Opsgenie, Slack 연동 | 임계치 초과 시 담당자 자동 호출 |

알림은 단순 임계치 알람에서 "사용자 경험에 실질적 영향을 주는 이상 징후만" 걸러내는 스마트 알림(alert fatigue 방지)으로 진화하고 있다.

### 6.2 장애 대응: 온콜 · 인시던트 관리 · 포스트모템

- **온콜(On-call) 체계**: 담당자가 교대로 대기하며 알림 발생 시 1차 대응, 무응답 시 상위 담당자로 자동 에스컬레이션.
- **인시던트 관리 프로세스**: 카카오는 "카카오 안정성 보고서(2023)"에서 장애를 3등급으로 분류하고, 감지→선언→처리→종료→후속조치의 **5단계 대응 프로세스**와 컨트롤타워·오퍼레이터·커뮤니케이터·운영책임자의 **4대 역할 체계**를 공식화했다.
- **포스트모템(Postmortem)/장애 회고**: Google SRE는 **"Blameless Postmortem(비난 없는 회고)"** 문화를 핵심 원칙으로 삼는다. 개인의 잘못을 추궁하지 않고 근본 원인과 재발 방지책만을 기록하며, 이렇게 축적된 포스트모템은 조직 전체의 신뢰성 자산이 된다.

### 6.3 서비스 지표 관리: SLA·SLO·SLI와 에러버짓

- **SLI(Service Level Indicator)**: 실측 지표 (예: "최근 한 달 가용률 99.95%")
- **SLO(Service Level Objective)**: 내부 목표치 (예: "가용률 99.9% 이상 유지")
- **SLA(Service Level Agreement)**: 대외 계약/보장 (미달 시 보상 등 포함)
- **에러버짓(Error Budget)**: 100% - SLO. 에러버짓 잔량에 따라 신규 기능 배포 속도를 조절(잔량 충분 → 적극 배포, 25% 미만 → 기능 동결)하는 **배포 속도와 안정성 사이의 의사결정 기준**이 된다.

무신사(MUSINSA)는 2주 만에 3개 서비스에 걸쳐 27개의 SLO와 54개의 모니터를 설정하고 배포까지 자동화한 사례를 공개했으며, LY Corporation(LINE)은 서비스별 SLI/SLO 설계 기준과 자체 상태 확인 도구(LINE Status) 개발 과정을 공유했다.

### 6.4 사용자 피드백 및 데이터 기반 개선

- **A/B 테스트 & 프로덕트 실험**: 가설 기반으로 대조군과 실험군을 나누어 지표 변화를 검증. Amplitude, Mixpanel 등은 자체 A/B 테스트·피처 플래그 기능을 내장해 실험→분석→배포를 하나의 플랫폼에서 처리한다.
- **프로덕트 애널리틱스**: Amplitude(예측 코호트, 생명주기 데이터 모델), Mixpanel(실시간 대시보드), GA(웹 트래픽/퍼널 분석).
- **정성적 피드백 채널**: 세션 리플레이, 인앱 설문, CS 문의, 앱스토어 리뷰 등이 정량 지표가 보여주지 못하는 "왜"를 보완한다.

### 6.5 실제 기업 사례 요약

| 기업 | 공개 사례 | 핵심 내용 |
|---|---|---|
| Google | SRE Book / Workbook | Blameless Postmortem, SLO/에러버짓 개념의 창시자 격 |
| Kakao | 카카오 안정성 보고서(2023) | 장애 3등급 분류, 5단계 대응 프로세스, 4대 역할 |
| Netflix | Chaos Engineering / Simian Army | Chaos Monkey·Chaos Kong으로 프로덕션 장애 유발 후 복원력 검증 |
| LY Corporation(LINE) | SLI/SLO 연재 | 서비스별 SLO 설계, LINE Status 개발 |
| MUSINSA | 무신사 테크블로그 | 2주 만에 27개 SLO·54개 모니터 구축 및 배포 자동화 |
| Toss | 사내 포스트모템 문화 개선 사례 | 구글 SRE 양식을 벤치마킹해 자체 회고 템플릿 고도화 |

## 7. 피드백 루프와 전체 프로세스 요약

운영/모니터링 단계는 독립된 마지막 단계가 아니라, **기획 단계로 다시 연결되는 순환 구조(Product Lifecycle Loop)**의 한 축이다.

```
기획/설계 → 개발 → 배포(CI/CD) → 운영·모니터링(APM/로그/알림)
     ↑                                        │
     │              SLI/SLO 측정, 에러버짓 소모율 확인
     │              장애 발생 시 온콜 대응 → 포스트모템
     │                                        │
     └── 회고·데이터 인사이트를 기획에 반영 ←──┘
              (재발 방지 대책 / 신규 요구사항 / 백로그 반영)
```

- **기술적 피드백 루프**: 장애·성능 데이터(SLO 미달, 에러버짓 소진)는 포스트모템을 거쳐 "재발 방지 액션 아이템"으로 정리되고, 다음 스프린트의 기술 부채 해소나 아키텍처 개선 계획에 반영된다.
- **제품 피드백 루프**: 사용자 행동 데이터(A/B 테스트 결과, 애널리틱스 지표, 정성적 피드백)는 PM에게 전달되어 다음 기획 사이클의 우선순위(백로그)를 조정하는 근거가 된다.
- **조직 문화 측면**: 이 루프가 실질적으로 작동하려면 "비난 없는" 심리적 안전감(blameless culture), 데이터를 투명하게 공유하는 문화(카카오의 공개 안정성 보고서 등), 지표(SLO/에러버짓) 기준의 명확한 배포 속도 의사결정 규칙이 함께 뒷받침되어야 한다.

결론적으로, 잘 만들어진 프로세스는 "장애를 얼마나 빨리 고치는가"뿐 아니라 "그 경험이 다음 기획과 설계에 얼마나 빠르고 정확하게 반영되는가"로 완성되며, 이것이 IT 서비스 조직이 지속적으로 신뢰성과 제품 경쟁력을 함께 끌어올리는 핵심 메커니즘이다.
